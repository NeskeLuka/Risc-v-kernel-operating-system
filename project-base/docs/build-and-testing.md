# Build, Run, and Test Guide

[Documentation index](README.md) · [Repository README](../../README.md)

## Required environment

The repository expects a Linux-style development environment with GNU Make, shell tools used by the Makefile, a RISC-V GCC/G++ and binutils toolchain, and `qemu-system-riscv64`. Its source targets `rv64ima`, `lp64`, and C++11 in a freestanding build.

These instructions describe the checked-in Makefile. They are not a claim of validation with every current compiler or QEMU release.

## Working directory and build

From the repository root:

```bash
cd "project-base"
make
make qemu
```

The quotes matter because the path contains a space. The Makefile probes the following toolchain prefixes in order:

1. `riscv64-unknown-elf-`
2. `riscv64-linux-gnu-`
3. `riscv64-unknown-linux-gnu-`

You can override the prefix explicitly:

```bash
make TOOLPREFIX=riscv64-unknown-elf-
make qemu TOOLPREFIX=riscv64-unknown-elf-
```

The link includes `lib/hw.lib`, `lib/mem.lib`, and `lib/console.lib`. Do not remove supplied libraries merely because the project also defines custom allocator and console classes.

## Build products and configuration

| Item | Meaning |
| --- | --- |
| `kernel` | Linked RISC-V image |
| `kernel.asm` | Source-annotated disassembly generated by objdump |
| `build/` | Objects, assembly listings, and dependency files |
| `kernel.ld` | `_entry` and image base at `0x80000000` |
| `CPU_CORE_COUNT = 1` | Single-CPU runtime configuration |
| `-m 128M` | 128 MiB QEMU RAM |
| `-bios none -nographic` | Supplied image startup and terminal I/O |

`make clean` deletes generated images and `build/`. Since the archive contains prebuilt `kernel` and `kernel.asm`, preserve them elsewhere if you want to compare those artifacts with a fresh build.

## Interactive test menu

`test/userMain.cpp` supplies the current application. The prompt **“Unesite broj testa? [1-9]”** asks for a test number. Enter a digit and press Enter; the input code consumes one following character as the newline. Start a fresh guest for each independent test.

| Option | Function actually called | What to observe |
| --- | --- | --- |
| 1 | `Threads_C_API_test()` | C-style thread creation, voluntary dispatch, register/stack exercise |
| 2 | `Threads_CPP_API_test()` | Subclass-based workers and dispatch |
| 3 | `producerConsumer_C_API()` | Producer/consumer buffering through C-style semaphores |
| 4 | `producerConsumer_CPP_Sync_API()` | C++ producers/consumer with explicit yields |
| 5 | `testSleeping()` | Two workers with 10- and 20-tick delays; main busy-waits, exercising preemption |
| 6 | `testConsumerProducer()` | C++ producers/consumer with relative sleeps |
| 7 | `System_Mode_test()` | A user worker reads privileged `sepc`; expected guest termination |
| 8 | `makeMatrix()` | Five row workers synchronize via semaphore; expected total is **28** |
| 9 | No test body | Prints a success-like message only; does not validate paired threads |

Options 3, 4, and 6 ask for the producer count and buffer capacity. Their input checks require at least one producer and producer count no larger than capacity. Escape (`0x1b`) ends keyboard production.

`LEVEL_2_IMPLEMENTED`, `LEVEL_3_IMPLEMENTED`, and `LEVEL_4_IMPLEMENTED` are enabled in the supplied entry point. `LEVEL_1_IMPLEMENTED` is zero, but that flag does not mean the custom memory allocator is absent. The menu is not a comprehensive allocation test suite.

Test 8's printed label mentions join, but the implementation uses repeated semaphore waits; there is no `Thread::join()` API. Test 7 should not reach its normal-success path: the kernel terminates the entire guest on the unhandled user trap.

## Additional tests

The Makefile recursively discovers source files, including `test/` and `myTests/`. Compiled functions are not automatically executed. To select an additional test, declare and call its entry function from the existing `userMain()`; keep exactly one `userMain` definition.

| Source | Entry point / purpose |
| --- | --- |
| `test/ThreadSuspended.cpp` | `threadSuspendChain()`; four-thread suspension experiment |
| `myTests/PeriodThreadTest.cpp` | `periodicMain()`; periodic activation and termination |
| `myTests/testZaAlokaciju.cpp` | `run_syscall_memory_test()`; data integrity, small allocations, fragmentation, coalescing exercise |
| `myTests/mojTest.cpp` | `cynhroneSemTest1()`; recursion, single-slot producer/consumer, multi-permit semaphores |
| `myTests/asynchroneThreadTest1.cpp` | `asynhroneThreadTest()`; mixed yielding, sleeping, and CPU work |
| `myTests/testSaNitima1.cpp` | `testSaNitima1()` / `testSaNitima2()`; console/thread experiments |
| `myTests/putcAndGetcTest.cpp` | `putGetTest()`; echo; `justGo()` is an unbounded output loop |
| `myTests/70Niti.cpp` | `Seventymain()`; 70-thread experiment with manual TCB deletion that conflicts with collector ownership |
| `myTests/workers.cpp` | Entire implementation is commented out |

Some experiments poll or delete raw TCB handles, which conflicts with automatic reclamation. Treat them as development experiments, not automatically safe reference programs. A stress-test filename alone does not establish a measured maximum supported thread count.

## Debugging support and build caveats

The Makefile contains `qemu-gdb`, but its `.gdbinit` rule depends on **`.gdbinit.tmpl-riscv`, which is absent from the supplied archive**. Supply a compatible template before relying on that target.

Assembly sources are collected with uppercase `.S`, while the explicit pattern rule mentions lowercase `.s`. Inspect the commands from `make -n` with your toolchain if assembly objects do not build; do not assume every Make implementation resolves this consistently.

If a newer assembler rejects CSR instructions under the supplied architecture flags, use the course-compatible toolchain or deliberately adapt the architecture options. Such a build change requires validation and was not made in this documentation update.

For context-switch investigations, inspect `kernel.asm` around trap entry, `updateResult`, and `TCB::contextSwitch`. Frame-pointer and inline-assembly assumptions are discussed in [Riscv](classes/Riscv.md).
